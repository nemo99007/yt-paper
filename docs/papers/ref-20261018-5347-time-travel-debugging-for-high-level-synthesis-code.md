## Detailed Summary

### Background and Problem

<div class="bi" markdown>
<div class="bi-en" markdown>

HLS designs are usually written in a C/C++ subset with libraries such as SystemC, so standard software tools (gcov, valgrind, sanitizers, GDB) apply. Traditional HLS debugging relies on "brute-force" logging, which is slow to review, requires rebuilding and re-running for each added datum, and often misses the root cause. SystemC models can contain thousands to tens of thousands of SC_THREAD/SC_METHOD processes, making races and deadlocks easy to introduce. Formal methods [6] and compiler analysis [7] need prior knowledge of the bug; static analyzers (Coverity) have false positives and negatives; dynamic detectors (ThreadSanitizer, Helgrind) can slow programs 10-100x and mostly flag shallow races; logging can serialize execution and hide races (Heisenbugs). The paper's goal is to introduce time-travel debugging and show it suits HLS.

</div>
<div class="bi-ko" markdown>

HLS 설계는 보통 SystemC 등 라이브러리를 포함한 C/C++ subset으로 작성되므로 gcov, valgrind, sanitizer, GDB 같은 표준 소프트웨어 도구를 사용할 수 있습니다. 전통적인 HLS 디버깅은 로그 출력에 의존하는 "brute-force" 방식이어서, 로그 검토가 느리고 데이터를 추가할 때마다 재빌드와 재실행이 필요하며, 근본 원인을 놓치는 경우가 많습니다. SystemC 모델은 수천에서 수만 개의 SC_THREAD/SC_METHOD를 포함할 수 있어 레이스 컨디션과 데드락이 쉽게 생깁니다. 형식 검증 [6]과 컴파일러 분석 [7]은 버그에 대한 사전 지식이 필요하고, 정적 분석기(Coverity)는 오탐과 미탐이 있으며, 동적 검출기(ThreadSanitizer, Helgrind)는 프로그램을 10-100배 느리게 만들고 주로 단순한 레이스만 찾습니다. 로깅은 실행을 직렬화하여 레이스를 가릴 수 있습니다(Heisenbug). 이 논문의 목표는 시간 여행 디버깅을 소개하고 HLS에 적합함을 보이는 것입니다.

</div>
</div>

### Architecture and Methodology

<div class="bi" markdown>
<div class="bi-en" markdown>

A time-travel debugger records execution and saves the results of non-deterministic events (system calls, user/kernel interactions, memory-mapped device register accesses). Replay recomputes memory and register state at any point, using intermittent snapshots for performance. Reverse commands (Table I) include step, next, finish, break, watch, continue and last. The key command is `last <expr>`, which sets a watchpoint and runs backwards to the previous modification.

</div>
<div class="bi-ko" markdown>

시간 여행 디버거는 실행을 기록하면서 비결정적 이벤트(시스템 콜, 사용자/커널 상호작용, 메모리 매핑 장치 레지스터 접근)의 결과를 저장합니다. 리플레이는 임의 시점의 메모리와 레지스터 상태를 다시 계산하며, 성능을 위해 중간 스냅샷을 사용합니다. 역방향 명령(표 I)에는 step, next, finish, break, watch, continue, last가 있습니다. 핵심 명령은 `last <expr>`로, 워치포인트를 설정하고 역방향으로 실행해 이전 수정 지점까지 되돌아갑니다.

</div>
</div>

```mermaid
    A[Record failing run] --> B[Stop at incorrect value]
    B --> C{Data or address wrong?}

    E --> F[last *request->data]
    F --> G[Root-cause line, e.g. mydata[i] += i]
    C -->|Address| H[Bookmark, explore other branch]
```

<div class="bi-en" markdown>

<div class="bi-ko" markdown>

설명된 사용 패턴:

<div class="bi" markdown>
<div class="bi-en" markdown>

- Worked example: from a wrong value stored in *data, `last` traces back through MEM[] and the request data to `mydata[i] += i`, without understanding intermediate code or all threads. Bookmarks allow returning from a wrong branch.

</div>
<div class="bi-ko" markdown>

- 실습 예: *data에 저장되는 잘못된 값에서 `last`로 MEM[]과 request 데이터를 거쳐 `mydata[i] += i` 라인까지 역추적합니다. 중간 코드나 모든 스레드를 이해할 필요가 없고, 북마크로 잘못된 분기에서 복귀할 수 있습니다.

</div>
</div>

<div class="bi" markdown>
<div class="bi-en" markdown>

- Race conditions: set a watchpoint on the incorrect variable and run backwards to see the modification sequence and reveal non-atomic accesses. Avoiding locks in HLS (to save latency, area and throughput) increases race risk.

</div>
<div class="bi-ko" markdown>

- 레이스 컨디션: 잘못된 변수에 워치포인트를 설정하고 역방향으로 실행해 수정 순서를 파악하며 non-atomic 접근을 드러냅니다. HLS에서는 락이 지연 시간, 면적, 처리량에 불리하므로 락을 피하려는 경향이 레이스 위험을 높입니다.

</div>
</div>

<div class="bi" markdown>
<div class="bi-en" markdown>

- Deadlocks: attach after stall, inspect thread backtraces, set breakpoints at lock and unlock points, and run in reverse to understand the sequence leading to the deadlock.

</div>
<div class="bi-ko" markdown>

- 데드락: 정지 후 연결하여 스레드 백트레이스를 확인하고, lock 및 unlock 지점에 브레이크포인트를 설정한 뒤 역방향으로 실행해 데드락에 이르는 순서를 분석합니다.

</div>
</div>

<div class="bi" markdown>
<div class="bi-en" markdown>

- Code discovery: start at any mid-execution breakpoint and explore how execution got there, variable and memory values, other thread states, and modifiers via watchpoints.

</div>
<div class="bi-ko" markdown>

- 코드 탐색: 실행 중간의 임의 브레이크포인트에서 시작해, 그 지점에 도달한 경로, 변수와 메모리 값, 다른 스레드 상태, 워치포인트로 수정 주체를 탐색합니다.

</div>
</div>

<div class="bi" markdown>
<div class="bi-en" markdown>

- Best practices: record failing regression tests (or all tests, at disk cost); design for debug by checking errors inside the same executable against a read-in reference; use intermediate variables for conditional breakpoints (optimized out in HDL synthesis); use assertions as sanity checks and debug backwards from where they fire.

</div>
<div class="bi-ko" markdown>

- 모범 사례: 실패한 회귀 테스트(또는 디스크 비용을 감수하고 전체 테스트)를 기록합니다. 읽어 들인 기준값과 같은 실행 파일 안에서 오류를 검사하는 design-for-debug를 적용합니다. 조건부 브레이크포인트에는 중간 변수를 사용할 수 있으며, 이 변수는 HDL 합성 중 최적화로 제거됩니다. 어서션은 가정 검증용 sanity checker로 쓰고, 발생 지점에서 역방향 디버그를 수행합니다.

</div>
</div>

<div class="bi" markdown>
<div class="bi-en" markdown>

- Waveforms: the paper shows a GTKWave view of a SystemC VCD example. It claims waveforms can also be extracted from a time-travel recording without rebuilding or re-running, and that a linked waveform viewer lets a click on a transition synchronize the debugger to that moment.

</div>
<div class="bi-ko" markdown>

- 파형: SystemC VCD 예제를 GTKWave로 보여줍니다. 논문은 시간 여행 녹화본에서도 재빌드나 재실행 없이 파형을 추출할 수 있다고 주장하며, 연결된 파형 뷰어에서 전이를 클릭하면 디버거가 해당 시점으로 동기화된다고 설명합니다.

</div>
</div>

<div class="bi" markdown>
<div class="bi-en" markdown>

Public tools: rr and Undo on Linux; Microsoft Time Travel Debugging on Windows. Limitations: slowdown depends heavily on workload; recording size is small compared with HDL simulation logs. Thread fuzzing is implemented for pthreads, so HLS libraries with their own schedulers need source-level modification; thread inspection has the same constraint.

</div>
<div class="bi-ko" markdown>

공개 도구: Linux에서는 rr과 Undo, Windows에서는 Microsoft Time Travel Debugging. 한계: 성능 저하는 워크로드에 따라 크게 달라지며, 녹화 크기는 HDL 시뮬레이션 로그에 비해 작습니다. 스레드 퍼징은 pthreads에 대해 구현되어 있어, 자체 스케줄러를 가진 HLS 라이브러리는 소스 수준 수정이 필요합니다. 스레드 정보 확인에도 같은 제약이 있습니다.

### Results and Conclusions

<div class="bi" markdown>
<div class="bi-en" markdown>

The authors state that they have seen data suggesting bug finding is often at least four times faster with time-travel debugging, which they describe as a 75% reduction in bug-finding time. They qualitatively link this to faster code learning, time-to-market, coverage closure, and shift-left testing (native x86, then FPGA, then silicon), and claim possible throughput and PPA benefits in modelling. The paper does not present the underlying dataset or a benchmark. Conclusion: time-travel debugging simplifies debugging and code exploration for HLS, and waveform export helps digital designers transition to HLS.

</div>
<div class="bi-ko" markdown>

저자들은 시간 여행 디버깅을 사용하면 버그 발견이 대개 최소 4배 빠르다는 데이터를 보았다고 밝히며, 이를 버그 탐색 시간 75% 감소에 해당한다고 설명합니다. 이것이 코드 학습 가속, time-to-market 단축, coverage closure, shift-left 조기 테스트(x86 네이티브, 이후 FPGA, 이후 실리콘)로 이어진다고 정성적으로 서술하며, 모델링 처리량과 PPA 개선 가능성도 주장합니다. 논문은 기반 데이터셋이나 벤치마크를 제시하지 않습니다. 결론적으로 시간 여행 디버깅은 HLS의 디버그와 코드 탐색을 단순화하며, 파형 내보내기는 디지털 설계 엔지니어의 HLS 전환을 돕습니다.</detailed_summary_ko>
