# Architectures to Tradeoff Performance vs. Debug for Software Development on Emulation Platform

## Summary

<div class="bi" markdown>
<div class="bi-en" markdown>

**Proposes two switchable emulation architectures that share the same RTL: a lock-step debug mode (DFA) with tracer and GDB/OpenOCD access, and a transaction-buffered performance mode (PFA), reaching about 2.24 MHz vs 26.92 kHz on a RISC-V SoC running CoreMark on Palladium.**

</div>
<div class="bi-ko" markdown>

**서로 동일한 RTL을 공유하는 두 가지 전환 가능한 에뮬레이션 아키텍처를 제안합니다. 하나는 tracer와 GDB/OpenOCD 접근을 갖춘 lock-step 디버그 모드(DFA)이고, 다른 하나는 트랜잭션 버퍼링을 사용하는 성능 모드(PFA)입니다. Palladium에서 CoreMark를 실행한 RISC-V SoC 기준으로 26.92 kHz에서 약 2.24 MHz로 향상되었습니다.**

</div>
</div>

## Key Insights

<div class="bi" markdown>
<div class="bi-en" markdown>

- Lock-step synchronization between the emulated DUT and the simulator-side testbench caps debuggable throughput: the debug-focused architecture ran at 26.92 kHz with 900,700 tbsyncs on CoreMark.

</div>
<div class="bi-ko" markdown>

- 에뮬레이션 DUT와 시뮬레이터 측 테스트벤치 사이의 lock-step 동기화가 디버그 가능 처리량을 제한합니다. 디버그 중심 아키텍처(DFA)는 CoreMark에서 900,700회의 tbsync와 함께 26.92 kHz로 동작했습니다.

</div>
</div>

<div class="bi" markdown>
<div class="bi-en" markdown>

- Decoupling the DUT clock from the testbench and buffering UART/GPIO transactions raised throughput to 2236.76 kHz with only 29 tbsyncs and 86.82% HW busy, versus 1.04% for DFA.

</div>
<div class="bi-ko" markdown>

- DUT 클록을 테스트벤치와 분리하고 UART/GPIO 트랜잭션을 버퍼링하자, PFA는 tbsync 29회, HW busy 86.82%로 2236.76 kHz에 도달했습니다. DFA의 HW busy는 1.04%였습니다.

</div>
</div>

<div class="bi" markdown>
<div class="bi-en" markdown>

- Keeping identical RTL across both modes makes bugs reproducible in either mode and shares synthesis effort; only the additional emulator-side components differ.

</div>
<div class="bi-ko" markdown>

- 두 모드에서 RTL을 동일하게 유지하면 한쪽 모드에서 발견된 버그를 다른 모드에서 재현할 수 있고 합성 작업을 공유할 수 있습니다. 차이는 에뮬레이터 측에 추가되는 컴포넌트뿐입니다.

</div>
</div>

<div class="bi" markdown>
<div class="bi-en" markdown>

- Instruction-level debug is obtained by tapping the Ibex RVFI interface into a simulator-side tracer and exposing GDB via OpenOCD, at the cost of signal-based acceleration overhead in DFA.

</div>
<div class="bi-ko" markdown>

- Ibex RVFI 인터페이스를 시뮬레이터 측 tracer에 연결하고 OpenOCD를 통해 GDB를 노출하여 명령어 단위 디버그를 구현했습니다. 대가로 DFA에서는 signal-based acceleration 오버헤드가 발생합니다.

</div>
</div>

<div class="bi" markdown>
<div class="bi-en" markdown>

- The evaluation is narrow: a single CoreMark benchmark on one internal Athos SoC on Palladium, with no quantitative comparison against hybrid or ICE modes beyond qualitative remarks.

</div>
<div class="bi-ko" markdown>

- 평가 범위가 좁습니다. 내부 Athos SoC 한 종에서 Palladium 기반 CoreMark 벤치마크 하나만 측정했고, 하이브리드 모드나 ICE 모드와의 정량 비교는 없고 정성적 언급에 그칩니다.

</div>
</div>

## Detailed Summary

### Background and Problem

<div class="bi" markdown>
<div class="bi-en" markdown>

- Software bring-up (boot code, security parameters, drivers, applications) must start before silicon, so the platform must balance fidelity against speed.

</div>
<div class="bi-ko" markdown>

- 소프트웨어 bring-up(boot code, 보안 파라미터, 드라이버, 애플리케이션)은 실리콘 이전에 시작되어야 하므로, 플랫폼은 충실도와 속도 사이의 균형을 맞춰야 합니다.

</div>
</div>

<div class="bi" markdown>
<div class="bi-en" markdown>

- Simulation is cycle-accurate with full visibility but runs at kHz speeds; ISS and virtual prototypes are fast but do not use the RTL, so RTL bugs stay hidden.

</div>
<div class="bi-ko" markdown>

- 시뮬레이션은 cycle-accurate하고 가시성이 뛰어나지만 kHz 수준으로 동작합니다. ISS와 가상 프로토타입은 빠르지만 RTL을 사용하지 않아 RTL 버그가 드러나지 않습니다.

</div>
</div>

<div class="bi" markdown>
<div class="bi-en" markdown>

- Emulation runs the real RTL, but in-circuit (ICE) mode is fast without debug access, while debuggable operation requires per-signal lock-step sync with the simulator, which the abstract puts at 10–100 kHz.

</div>
<div class="bi-ko" markdown>

- 에뮬레이션은 실제 RTL을 실행하지만, in-circuit(ICE) 모드는 디버그 접근이 없이 빠르고, 디버그 가능 동작은 시뮬레이터와의 신호 단위 lock-step 동기화를 요구합니다. 초록에 따르면 이 경우 10–100 kHz 수준입니다.

</div>
</div>

### Architecture and Methodology

<div class="bi" markdown>
<div class="bi-en" markdown>

- Both modes use the same RTL. The debug-focused architecture (DFA) runs the SoC on the emulator, with a Linux-side simulator hosting virtual peripherals, a GDB-facing debugger interface, and an Ibex RVFI-based instruction tracer. Signal-based acceleration and a shared clock keep the testbench cycle-synchronized.

</div>
<div class="bi-ko" markdown>

- 두 모드 모두 동일한 RTL을 사용합니다. 디버그 중심 아키텍처(DFA)는 에뮬레이터에서 SoC를 실행하고, Linux 측 시뮬레이터에 가상 주변장치, GDB 연동 디버거 인터페이스, Ibex RVFI 기반 명령어 tracer를 둡니다. Signal-based acceleration과 공유 클록으로 테스트벤치를 cycle 단위로 동기화합니다.

</div>
</div>

<div class="bi" markdown>
<div class="bi-en" markdown>

- The performance-focused architecture (PFA) keeps the SoC and its clock/reset generator (defined by a qel file, CAKE API) on the emulator, with a transaction buffer that captures UART/GPIO output and is polled periodically by the simulator. The simulator runs only virtual GPIO/UART on an independent clock.

</div>
<div class="bi-ko" markdown>

- 성능 중심 아키텍처(PFA)는 SoC와 클록/리셋 생성기(qel 파일과 CAKE API로 정의)를 에뮬레이터에 두고, UART/GPIO 출력을 캡처하는 트랜잭션 버퍼를 둡니다. 시뮬레이터는 이 버퍼를 주기적으로 읽습니다. 시뮬레이터에는 독립 클록으로 구동되는 가상 GPIO/UART만 남습니다.

</div>
</div>

<div class="bi" markdown>
<div class="bi-en" markdown>

- Target: the internal Athos RISC-V SoC (Ibex core, TileLink buses), built with ProtoForge and compiled with the RISC-V toolchain.

</div>
<div class="bi-ko" markdown>

- 대상: 내부 Athos RISC-V SoC(Ibex 코어, TileLink 버스). ProtoForge로 빌드하고 RISC-V toolchain으로 컴파일했습니다.

</div>
</div>

### Results and Conclusions

<div class="bi" markdown>
<div class="bi-en" markdown>

- CoreMark on Palladium: DFA 26.92 kHz, 900,700 tbsyncs, 1.04% HW busy; PFA (with dumping) 2236.76 kHz, 29 tbsyncs, 86.82% HW busy.

</div>
<div class="bi-ko" markdown>

- Palladium의 CoreMark 결과: DFA 26.92 kHz, tbsync 900,700회, HW busy 1.04%. PFA(덤프 활성화) 2236.76 kHz, tbsync 29회, HW busy 86.82%.

</div>
</div>

<div class="bi" markdown>
<div class="bi-en" markdown>

- The table values imply roughly 83x, and the paper states "close to 100x" for DFA vs PFA.

</div>
<div class="bi-ko" markdown>

- 표의 값으로 계산하면 약 83배이며, 논문은 DFA 대비 PFA가 "close to 100x"라고 밝힙니다.

</div>
</div>

<div class="bi" markdown>
<div class="bi-en" markdown>

- The authors recommend PFA for nightly regressions and DFA for debugging failures, with mode switching in the same testbench infrastructure. Results come from a single benchmark on one SoC, so generality is unproven.

</div>
<div class="bi-ko" markdown>

- 저자들은 야간 회귀에는 PFA, 실패 디버그에는 DFA를 권장하며, 두 모드는 같은 테스트벤치 인프라에서 전환됩니다. 결과는 단일 벤치마크와 단일 SoC에서 얻은 것이므로 일반화는 검증되지 않았습니다.

</div>
</div>
