<div class="bi" markdown>
<div class="bi-en" markdown>

**HPE가 ASIC 검증 데이터(컴퓨터 팜, 라이선스, 성능, 테스트 결과, 커버리지)를 수집·분석해 라이선스 낭비·성능 저하·시뮬레이션 slowdown의 근본 원인을 찾고 예측 정확도를 높인 사례와, 오픈소스 중심의 Big Data 툴체인 구성법을 소개한 논문.**

## Key Insights

<div class="bi" markdown>
<div class="bi-en" markdown>

- 라이선스 병목은 실제 수요와 기대 수요의 차이를 시계열로 보면 드러난다. 예: 대기 작업 스파이크는 CI 잡이 같은 시각에 몰린 결과였고, 시차 분산으로 평탄화했다.

</div>
<div class="bi-ko" markdown>

&nbsp;

</div>
</div>

<div class="bi" markdown>
<div class="bi-en" markdown>

- 예약(reserved) 라이선스 상태 분석으로, 라이선스가 필요 없는 후처리 스크립트가 라이선스를 점유하던 문제와 컴파일 단계의 불필요한 라이선스 점유를 찾아 구매 없이 처리량을 개선했다.

</div>
<div class="bi-ko" markdown>

&nbsp;

</div>
</div>

<div class="bi" markdown>
<div class="bi-en" markdown>

- 성능 회귀는 자동 아웃라이어 탐지 + nightly 자동 플롯으로 조기에 잡을 수 있다. 사례에서는 스티뮬러스 버그(데이터 전송 명령이 시뮬 초반에 몰림)가 성능 수치를 비현실적으로 높게 만들고 있었다.

</div>
<div class="bi-ko" markdown>

&nbsp;

</div>
</div>

<div class="bi" markdown>
<div class="bi-en" markdown>

- 시뮬레이션 6배 지연의 원인이 testbench 변경으로 인한 메모리 요구 증가 → garbage collection 폭증으로 밝혀졌다. 실행 시간과 GC 횟수 등 시뮬레이터 메타데이터를 함께 수집하는 것이 원인 추적에 핵심이다.

## Detailed Summary

<div class="bi" markdown>
<div class="bi-en" markdown>

### 배경 및 문제 정의

</div>
<div class="bi-ko" markdown>

&nbsp;

</div>
</div>

<div class="bi" markdown>
<div class="bi-en" markdown>

HPE는 ASIC 개발에서 제품을 더 빨리 시장에 내놓기 위해, 검증 과정의 데이터를 활용해 라이선스·컴퓨트 자원·엔지니어링 인력·일정을 더 정확히 예측하고 검증 엔지니어가 더 나은 결정을 내리도록 하고자 했다. 논문은 "Big Data가 ASIC 검증에도 적용되는가?"라는 질문에서 출발해, 대규모 NoSQL이나 MapReduce, AI 없이도 수 GB 규모 데이터를 일반적인 도구로 분석해 가치를 얻을 수 있다고 주장한다. 핵심 목표는 테스트벤치나 체커를 바꾸지 않고도 시뮬레이션 처리량, DUT 성능(대역폭·지연), 커버리지 분석을 개선해 버그를 더 빨리 찾는 것이다.

</div>
<div class="bi-ko" markdown>

&nbsp;

</div>
</div>

<div class="bi" markdown>
<div class="bi-en" markdown>

### 핵심 아키텍처 및 방법론

</div>
<div class="bi-ko" markdown>

&nbsp;

</div>
</div>

<div class="bi" markdown>
<div class="bi-en" markdown>

논문은 데이터 분야를 네 가지로 나눈다.

</div>
<div class="bi-ko" markdown>

&nbsp;

</div>
</div>

<div class="bi" markdown>
<div class="bi-en" markdown>

| 분야 | 수집 데이터 예 | 규모(문서 기재) |
|---|---|---|
| Compute Farm Metrics | 잡 데이터, 라이선스 사용량, 디스크, 시스템 부하 (6분 간격) | 약 400M rows/년 |
| Performance Data | 인터페이스별 대역폭·지연·사용률 | 약 20M rows/년 |
| Test Results Data | 테스트 이름, 메타데이터, pass/fail, 실행 시간, 메모리 | 약 70M rows/년 |
| Big Coverage Data | 커버리지 이벤트별 값과 시뮬 시간 | 약 100B rows/월 (~1 TB/월) |

</div>
<div class="bi-ko" markdown>

&nbsp;

</div>
</div>

<div class="bi" markdown>
<div class="bi-en" markdown>

- **Compute farm**: 라이선스 서버와 잡 매니저 데이터를 결합해 실제 수요 대 기대 수요를 비교한다. CI 잡이 같은 시각에 시작되어 생긴 수요 스파이크를 시간 분산으로 평탄화했다.

</div>
<div class="bi-ko" markdown>

&nbsp;

</div>
</div>

<div class="bi" markdown>
<div class="bi-en" markdown>

- **Performance (Autoperf)**: 설계를 계측하고 측정값을 비정형 데이터로 Vertica DB에 저장하며, 웹 앱으로 보여준다. 야간 회귀에서 이상값 탐지 기법으로 실패를 자동 보고한다.

</div>
<div class="bi-ko" markdown>

&nbsp;

</div>
</div>

<div class="bi" markdown>
<div class="bi-en" markdown>

- **Test results**: 테스트별 실행 사이클 배분, 회귀 우선순위(긴 테스트·지난 회귀 실패 테스트 먼저 실행), 시뮬레이션 성능 저하, CPU·메모리 구성, 라이선스 시간 기반 예측에 쓴다.

</div>
<div class="bi-ko" markdown>

&nbsp;

</div>
</div>

<div class="bi" markdown>
<div class="bi-en" markdown>

- **Big Coverage**: 커버리지를 단순 hit 기록이 아니라 신호의 모든 값 변화와 이벤트로 저장하는 방식을 제안한다. 구성 요소는 (1) 수 TB 규모의 빠른 DB, (2) XML 명세로부터 Verilog 계측 코드를 생성하는 스크립트와 ASCII 로그 변환기, (3) waveform 형태의 함수형 질의를 제공하는 웹 앱(primitive: add, mask, integrate, max 등), (4) 외부 도구·watchdog용 REST 서비스다. 대표 subset만 기본 기록하고 명령줄 스위치로 필요 시 기록하며, 파생 메트릭은 보존 기간을 길게 둔다.

</div>
<div class="bi-ko" markdown>

&nbsp;

</div>
</div>

<div class="bi" markdown>
<div class="bi-en" markdown>

- **툴킷**: MySQL/MariaDB/Postgres 같은 구조화 DB와 Hadoop/Vertica 같은 비정형 DB, Perl/Python 스크립트, ChartJS·Grafana 등 시각화 도구를 조합한다. 논문은 이 흐름을 소규모 팀이 약 1 엔지니어-월로 구축하고 월 몇 시간 정도로 유지할 수 있다고 주장한다.

</div>

<div class="bi-en" markdown>

### 실험 결과 및 결론

</div>
<div class="bi-ko" markdown>

&nbsp;

</div>
</div>

<div class="bi" markdown>
<div class="bi-en" markdown>

논문은 정량적 벤치마크가 아니라 실무 사례 중심으로 결과를 보고한다(본문에 명시된 수치 위주).

</div>
<div class="bi-ko" markdown>

&nbsp;

</div>
</div>

<div class="bi" markdown>
<div class="bi-en" markdown>

1. **라이선스 기아(starvation)**: 대기 잡 스파이크와 버퍼 한계 이하로 떨어진 가용 라이선스를 찾았다. 원인은 한 비즈니스 그룹이 할당을 초과 사용한 것이며, 사용자에게 자원 요청을 수정하도록 해 해결했다. 같은 시각 CI 잡 집중도 분산했다.

</div>
<div class="bi-ko" markdown>

&nbsp;

</div>
</div>

<div class="bi" markdown>
<div class="bi-en" markdown>

2. **라이선스 예약 상태**: 라이선스 사용률이 약 90%에 그친 원인은 (a) 라이선스가 필요 없는 후처리 스크립트가 라이선스를 점유한 것, (b) 컴파일이 전 구간 라이선스를 잡고 있던 것이었다. 도구 수정과 벤더 협의로 추가 구매 없이 라이선스당 처리량을 높였다.

</div>
<div class="bi-ko" markdown>

&nbsp;

</div>
</div>

<div class="bi" markdown>
<div class="bi-en" markdown>

3. **성능 저하**: 데이터 mover 대역폭이 급락한 사건에서, 4/17 데이터는 전송 명령이 시뮬레이션 초반에 몰려 읽히는 스티뮬러스 버그를 보였고, 4/22에는 전 구간에 분산되어 수정이 확인되었다. 논문은 성능이 기대보다 높게 나온 것 자체가 두 번째 버그였다고 평가한다.

</div>
<div class="bi-ko" markdown>

&nbsp;

</div>
</div>

<div class="bi" markdown>
<div class="bi-en" markdown>

4. **시뮬레이션 6배 지연**: 실행 시간 급증과 GC 횟수 증가의 상관관계를 찾았고, testbench 변경으로 메모리 요구가 늘었지만 테스트의 요청 메모리는 그대로여서 GC thrashing이 발생했음을 밝혔다. 메모리 요청을 늘리고 TB를 최적화해 해결했다.

</div>
<div class="bi-ko" markdown>

&nbsp;

</div>
</div>

<div class="bi" markdown>
<div class="bi-en" markdown>

**결론**: 저자들은 데이터 수집 설계와 올바른 질문이 핵심이며, 오픈소스 중심 툴로도 Big Data 인프라를 구축할 수 있다고 결론짓는다. 향후 과제는 (1) EDA 벤더 커버리지를 비정형 DB로 저장, (2) 테스트 결과를 Hadoop으로 분석, (3) AI/ML 기반 stimulus 생성, (4) 여러 데이터 도메인을 가로지르는 질의다. 다만 커버리지 전면 계측은 DB 부담이 크므로 희귀 corner-case 커버포인트는 기존 functional coverage를 유지한다는 한계도 명시한다.
