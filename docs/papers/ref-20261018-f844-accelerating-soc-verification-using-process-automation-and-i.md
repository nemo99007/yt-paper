## Summary

<div class="bi" markdown>
<div class="bi-en" markdown>

**A Samsung platform that integrates existing IP, block, and SoC verification workflows bottom-up through automation modules (flow controller, regression manager, job scheduler, triage, data manager), reporting 27–43% verification time reduction per verification level in actual projects.**

</div>
<div class="bi-ko" markdown>

**기존 IP, 블록, SoC 검증 워크플로를 bottom-up 방식으로 통합하는 Samsung 플랫폼으로, flow controller, regression manager, job scheduler, triage, data manager 모듈로 구성되며 실제 프로젝트에서 검증 레벨별로 27~43%의 검증 시간 단축을 보고합니다.**

</div>

## Key Insights

<div class="bi" markdown>
<div class="bi-en" markdown>

- Integration was done bottom-up with an interface layer over existing per-engineer environments, rather than forcing a unified top-down environment, to limit verification stability risk.

</div>
<div class="bi-ko" markdown>

- 기존 개인별 환경을 강제로 통합하는 top-down 방식 대신, 검증 안정성 위험을 줄이기 위해 인터페이스 계층으로 기존 환경을 감싸는 bottom-up 방식으로 통합했습니다.

</div>
</div>

<div class="bi" markdown>
<div class="bi-en" markdown>

- Verification time reduction reported per level: about 35% at VL1, 43% at VL2, 28% at VL3, and 27% at VL4, with up to 43% per step when triage is applied to failing cases.

</div>
<div class="bi-ko" markdown>

- 레벨별 검증 시간 단축은 VL1 약 35%, VL2 43%, VL3 28%, VL4 27%이며, triage를 실패 케이스에 적용한 단계에서는 최대 43%로 보고됩니다.

## Detailed Summary

### Background and Problem

<div class="bi" markdown>
<div class="bi-en" markdown>

- SoC size and complexity keep rising while TAT pressure grows; each project is split into IP, block, and top-level stages, each with per-engineer scripts and environments that are hard to keep consistent and prone to manual error.

</div>
<div class="bi-ko" markdown>

- SoC 규모와 복잡도가 커지는 한편 TAT 압박도 커지고 있으며, 프로젝트는 IP, 블록, 탑 레벨로 나뉘고 각 단계마다 개인별 스크립트와 환경이 존재해 일관성 유지가 어렵고 수작업 오류가 발생하기 쉽습니다.

</div>
</div>

<div class="bi" markdown>
<div class="bi-en" markdown>

- Verification is defined in four levels (VL1–VL4). Existing IP, block, and SoC verification runs largely separately and is not synchronized with top-level verification.

</div>
<div class="bi-ko" markdown>

- 검증은 VL1–VL4의 4개 레벨로 정의되며, 기존 IP, 블록, SoC 검증은 대체로 분리되어 수행되고 탑 레벨 검증과 동기화되지 않습니다.

</div>
</div>

### Architecture and Methodology

<div class="bi" markdown>
<div class="bi-en" markdown>

- Bottom-up integration: an interface layer wraps existing environments instead of unifying them top-down, to limit stability risk.

</div>
<div class="bi-ko" markdown>

- Bottom-up 통합: 안정성 위험을 줄이기 위해 기존 환경을 강제로 통합하지 않고 인터페이스 계층으로 감쌉니다.

</div>
</div>

<div class="bi" markdown>
<div class="bi-en" markdown>

- Five modules: Flow controller (scenarios of pre/body/post steps, reusable and CI-like), Regression Manager (wraps a commercial regression tool, metadata-driven), Job Scheduler (priority or reserved-time jobs, actor groups, scenario-level status), Triage Scenario (binary search and density-based clustering to reorder failing tests), and Data Manager (stores RTL change history and results, dashboard and mail reporting).

</div>
<div class="bi-ko" markdown>

- 5개 모듈: Flow controller(pre/body/post 스텝으로 구성된 재사용 가능한 시나리오, CI와 유사), Regression Manager(상용 회귀 도구를 감싸며 메타데이터 기반 동작), Job Scheduler(우선순위 또는 예약 시간 기반 작업, actor 그룹, 시나리오 단위 상태 관리), Triage Scenario(binary search와 density-based clustering으로 실패 테스트 재정렬), Data Manager(RTL 변경 이력과 결과 저장, dashboard 및 메일 보고).

</div>
</div>

### Results and Conclusions

<div class="bi" markdown>
<div class="bi-en" markdown>

- Time model: with parallel runs, VL2 and above take the max of sub-level runtimes; the VL1 example gives 16T versus 20T before.

</div>
<div class="bi-ko" markdown>

- 시간 모델: 병렬 실행을 가정하여 VL2 이상은 하위 레벨 실행 시간의 최댓값을 사용하며, VL1 예시는 기존 20T 대비 16T가 됩니다.

</div>
</div>

<div class="bi" markdown>
<div class="bi-en" markdown>

- Measured reductions: VL1 about 35%, VL2 43%, VL3 28%, VL4 27%; up to 43% per step with triage on failing cases.

</div>
<div class="bi-ko" markdown>

- 측정된 단축률: VL1 약 35%, VL2 43%, VL3 28%, VL4 27%이며, 실패 케이스에 triage를 적용한 단계에서는 최대 43%입니다.

</div>
</div>

<div class="bi" markdown>
<div class="bi-en" markdown>

- Results come from partial application in a flagship mobile AP SoC project and are not statistically analyzed. Future work: clustering-based test reordering, a classifier for sanity tests, and dynamic distributed scheduling.

</div>
<div class="bi-ko" markdown>

- 결과는 플래그십 모바일 AP SoC 프로젝트에서의 부분 적용에 기반하며 통계 분석은 제시되지 않았습니다. 향후 과제로 클러스터링 기반 테스트 재정렬, sanity 테스트용 분류기, 동적 분산 스케줄링이 제시되었습니다.

</div>
</div>
