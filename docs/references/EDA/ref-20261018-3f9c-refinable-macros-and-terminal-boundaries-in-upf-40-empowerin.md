# Refinable Macros and Terminal Boundaries in UPF 4.0: Empowering Soft IPs of the Future

[:material-open-in-new: 원문 보기](https://dvcon-proceedings.org/wp-content/uploads/1082.pdf){ .md-button .md-button--primary target=_blank }

> UPF 4.0의 Refinable Macro는 IP의 검증된 power intent를 바꾸지 않고 SoC 통합 단계에서 구현 세부사항(isolation 위치, power switch 등)을 비침투적으로 추가할 수 있게 하며, Terminal Boundary 표기로 도구 간 해석 불일치(시뮬레이션 vs 합성)를 줄이는 방법을 제시한다.

## 핵심 인사이트

- UPF 3.1의 Soft Macro는 terminal boundary로서 상위 power intent 수정을 막아 SoC 레벨 최적화와 충돌하며, 이로 인해 설계자가 IP UPF를 직접 수정하고 재검증해야 하는 위험이 있었다.
- UPF 4.0 Refinable Macro는 set_design_attributes -is_refinable_macro (또는 UPF_is_refinable_macro TRUE)로 지정되며, load_upf -implementation으로 허용된 명령 집합(Table 1)만 적용해 원본 power intent를 보존한 채 구현 세부사항을 추가한다.
- Path-based isolation 전략은 전역 설계 가시성이 필요해 시뮬레이션과 합성 간 isolation cell 삽입 불일치를 낳을 수 있으며, terminal boundary 마킹이 이 탐색 범위를 제한하는 역할을 한다.
- 문서의 예시에서 -location 옵션이 IP 측에서 지정되지 않으면 SoC 통합자가 PnR 요구에 맞춰 isolation 위치를 결정할 수 있는데, 이는 IP 측이 명시적으로 고정한 -location은 override할 수 없다는 제약과 함께 적용된다.

## 상세 요약

### 배경 및 문제 정의

SoC에는 각각 고유한 power management 구조를 가진 다수의 Soft IP(SIP)가 통합되는 추세다. SIP는 보통 기술 독립적인 UPF 파일로 power intent를 제공하지만, synthesis·PnR 단계에서 구현 세부사항을 추가해야 하며 이 과정에서 IP 검증 무결성이 깨질 위험이 있다.

문서가 지적하는 UPF 3.1의 한계는 다음과 같다.

- **Successive Refinement**: Constraint UPF → Configuration UPF → Implementation UPF로 이어지는 단계적 정제 방법론은 bottom-up **implementation** 흐름을 주로 지원하며, bottom-up **verification** 흐름에 대한 semantics가 부족하다.
- **Soft Macro**: 독립 구현을 전제로 terminal boundary를 형성해 내부 power intent를 외부 변경으로부터 보호한다. 그러나 상위 scope에서 power intent를 정제할 수 없어 SoC 수준 최적화를 막는다.
- **결과**: 설계자는 (1) SIP UPF를 그대로 두고 통합 시 예외 처리를 하거나 (2) IP를 Soft Macro로 지정해 최적화를 포기하거나, 둘 중 하나를 택해야 하며, 어느 쪽도 검증 무결성과 유연성을 동시에 만족하지 못한다.

문서는 이전 연구(Verification Macros, DVCon US 2023)의 후속으로, UPF 4.0([IEEE 1801-2024])이 이러한 한계를 체계적으로 해결한다고 주장한다.

### 핵심 아키텍처 및 방법론

**1. Refinable Macro 정의**

Refinable Macro는 SoC 통합자가 IP의 원본 UPF를 바꾸지 않고 구현 세부사항을 추가할 수 있게 하는 refinable terminal boundary다. 지정 방법은 다음과 같다.

```
set_design_attributes -models SIP \
    -attribute {UPF_is_refinable_macro TRUE}

# 또는 현재 scope 모델 지정
set_design_attributes -models {.} -is_refinable_macro
```

**2. Implementation UPF 및 허용 명령**

정제 내용은 Implementation UPF에 작성되며, 기본 power architecture를 바꾸지 않는 명령만 허용된다. 문서의 Table 1에 따르면 허용 범주는 다음과 같다.

- 포트/넷 생성 및 연결: `create_logic_port`, `create_supply_net`, `connect_supply_net` 등
- Power switch 및 셀 매핑: `create_power_switch`, `map_power_switch`, `map_retention_cell` 등
- 기존 객체 갱신(`-update`): `create_power_domain -update`(일부 옵션), `set_isolation -update`(일부 옵션), `set_retention -update`(-instance, -retention_supply만) 등
- 전략 정의: `set_isolation`, `set_level_shifter`, `set_repeater`
- 속성 및 scope 관리: `set_design_attributes`, `set_port_attributes`, `set_scope`, `load_upf`

적용은 다음과 같이 한다.

```
load_upf ip.socimpl.upf -scope ip1 -implementation
```

**3. Terminal Boundary 의미론**

Path-based isolation은 교차 도메인 경로를 자동 분석하므로 전역 가시성이 필요하다. Terminal boundary는 교차 도메인 추적을 경계에서 멈추고, 경계 포트의 driver/receiver supply 조건에 의존하게 한다. UPF는 세 가지 macro를 terminal boundary로 정의한다.

- Soft Macro (UPF 3.1): 독립 구현용, power intent 캡슐화
- Hard Macro (UPF 3.1): 사전 구현된 고정 기능·power intent
- Refinable Macro (UPF 4.0): 원본 power intent를 보존하며 비침투적 정제 허용

**4. 시뮬레이션–합성 불일치 사례 (Figure 4)**

두 입력 supply로 내부를 구동하는 IP가 SoC에서 여러 번 인스턴스화되고, 일부 인스턴스에서 두 supply가 단락될 수 있다. 합성 단계는 standalone 기준으로 isolation cell을 삽입해 모든 인스턴스가 이 netlist를 공유하지만, RTL 시뮬레이션은 supply 단락을 반영해 isolation cell을 생략한다. 그 결과 정상 동작 중 잘못된 clamping 같은 문제가 시뮬레이션에서 드러나지 않을 수 있다. Soft Macro로 표시하면 시뮬레이션도 합성 시 추론된 isolation cell을 유지하게 되어 일치한다.

**5. 통합 예시 (Section VI)**

- IP UPF(`ip.upf`): `set_design_attributes -models {.} -is_refinable_macro true`로 자신을 Refinable Macro로 지정하고, AON/PGD 도메인과 `o_PGD_to_AON` isolation 전략을 정의하되 `-location`은 생략한다. 단, IP가 `-location`을 하드코딩했다면 Refinable Macro 정제로 override할 수 없다.
- SoC 구현 UPF(`ip.socimpl.upf`): `set_isolation o_PGD_to_AON -domain PGD -location self -update`로 위치만 지정한다.
- SoC UPF(`parIP1.upf`): `load_upf ip.upf -scope ip1`과 `load_upf ip.socimpl.upf -scope ip1 -implementation`으로 두 파일을 로드한다.

### 실험 결과 및 결론

본 문서는 정량적 실험 결과(성능, 면적, 검증 시간 수치)를 제시하지 않는다. 주장하는 효과는 정성적이며 다음과 같다.

- **유연성**: 통합자가 PnR 요구에 맞게 isolation 위치 등을 정할 수 있다.
- **검증 무결성**: IP의 원본 power intent와 standalone 검증이 유지되어 재검증이 줄어든다.
- **도구 일관성**: Terminal boundary로 시뮬레이션과 합성 간 불일치를 줄이고, 경계 기준 분할로 병렬 처리가 가능해진다.
- **도구 강제**: 도구가 허용되지 않은 정제를 거부하도록 강제한다.

문서는 Refinable Macro와 Terminal Boundary가 UPF 4.0에서 SIP 통합의 유연성과 검증 무결성을 함께 확보한다고 결론짓는다. 다만 Table 2의 표현이 간략하고, 도구별 구현 지원 현황이나 실제 프로젝트 데이터는 포함되지 않아 실무 적용 시에는 해당 EDA 도구의 UPF 4.0 지원 범위를 별도로 확인해야 한다. 또한 본문은 Section VI를 "case study"라고 부르지만 단일 예시만 다룬다.
