# Pragmatic Verification Reuse in a Vertical World

[:material-open-in-new: 원문 보기](https://dvcon-proceedings.org/wp-content/uploads/pragmatic-verification-reuse-in-a-vertical-world.pdf){ .md-button .md-button--primary target=_blank }

> 블록 레벨 검증 환경을 탑 레벨에서 재사용할 때 발생하는 역할 변화(active→passive)를 중심으로, 수동(passive) 모드 설계, 캡슐화, 네임스페이스, 커버리지 튜닝 등 실무 가이드라인을 정리한 논문.

## 핵심 인사이트

- 스코어보드를 active 컴포넌트(sequence item/driver)에 연결하는 것은 블록→탑 재사용을 근본적으로 무력화하는 가장 흔하고 복구하기 어려운 설계 결함이며, 스코어보드 입력은 반드시 모니터가 실제 트래픽을 디코딩해 발행한 트랜잭션이어야 한다.
- 프로토콜 체크, 기능 커버리지, 중요 메시지, 설정 갱신은 모두 passive 컴포넌트(주로 모니터)에 두어야 탑 레벨에서 살아남는다. 드라이버에만 있는 체크/커버리지는 탑 레벨 검증 목표에 기여하지 못한다.
- active/passive 플래그는 서브컴포넌트뿐 아니라 최상위 환경 전체에 적용해야 하며, 탑 레벨 integrator가 하나의 환경 객체와 하나의 hierarchical interface만 다루도록 캡슐화하는 것이 핵심이다.
- SVA 프로토콜 체크는 인터페이스 안에 두어 passive 모드에서도 동작하게 하고, 패키지 네임스페이스 충돌을 막기 위해 모든 패키지 항목에 컴포넌트 고유 prefix를 붙여야 한다(예: BUS_WIDTH 매크로, 짧은 enum 리터럴 충돌).
- 블록 RTL assertion과 AMS assertion은 탑 레벨에서 성능과 false sense of security를 유발할 수 있어 개별 on/off 제어가 가능해야 하며, formal의 assume은 시뮬레이션에서 assert로 재사용해 검증해야 한다.

## 상세 요약

### 배경 및 문제 정의

블록 레벨 검증 환경을 탑 레벨(sub-system/top-level)에서 재사용하면 외부 인터페이스 검증에 더해 내부 체크, 커버리지, 메시지를 제공해 버그 검출과 디버그 속도를 높일 수 있다. 그럼에도 여러 회사와 프로젝트에서 이러한 vertical reuse가 일관되게 달성되지 않는다는 것이 문제 제기의 출발점이다. 논문은 UVM 같은 방법론이 이를 지원한다고 알려져 있지만 실제로는 잘 되지 않는 이유를 근본부터 다시 살펴본다.

저자는 vertical reuse를 "역할(role)이 바뀌는 계층 간 재사용"으로 정의한다. 블록에서는 active(자극 생성)였던 컴포넌트가 탑에서는 passive(관찰·체크 전용)로 쓰이는 것이 핵심 변화다. 또한 실제 현장에서는 탑 레벨 환경이 블록 환경과 병행 개발되고, 블록 환경의 품질과 능력이 제각각이어서 bottom-up 방식의 깔끔한 계층화가 현실적으로 어렵다고 지적한다.

### 핵심 아키텍처 및 방법론

논문은 active/passive 모드 설계를 중심으로 실무 가이드라인을 제시한다. 주요 원칙은 다음과 같다.

- **Active/Passive 설정**: 모든 서브컴포넌트가 flag를 가져야 하며, 환경 전체가 이 설정을 고려해야 한다. passive 생성 시 sequencer/driver를 만들지 않고, 그 포트나 참조를 연결하지 않는다.
- **스코어보드**: passive 환경에 있으므로 입력은 반드시 passive 모니터가 실제 신호를 디코딩해 analysis port로 발행한 트랜잭션이어야 한다. sequence item을 스코어보드로 보내는 단축은 재사용을 무너뜨린다.
- **기능 체크와 커버리지**: 프로토콜/타이밍 체크, 메시지, 기능 커버리지는 모니터에 둔다. 커버리지는 요청한 트랜잭션이 아니라 실제 관찰된 트래픽을 기준으로 해야 한다. 에러 인젝션처럼 모니터가 디코딩할 수 없는 자극 커버리지만 드라이버에 둘 수 있으나 탑에서는 재사용되지 않는다.
- **설정 갱신**: 설정 값은 시퀀스나 드라이버가 아니라 모니터 같은 passive 컴포넌트가 갱신한다.
- **경고 승격**: 블록에서 warning으로 처리하던 illegal 트랜잭션은 passive 모드에서 error로 승격해 상위 RTL 문제를 드러낼 수 있다.
- **테스트 종료**: passive 컴포넌트는 test objection을 걸지 않는다. 내부 인터페이스의 부분 트랜잭션이나 DMA는 탑 시나리오에 따라 중단될 수 있기 때문이다.
- **Stimulus 재사용**: sequence item에는 legality 제약만 두고, 분포 등 사용자 제약은 sequence에 둔다. 블록 공급자는 고수준 기능 sequence 라이브러리를 함께 제공하고 단일 라이브러리로 캡슐화한다.
- **캡슐화**: 전체 서브컴포넌트를 base-test가 아닌 단일 environment 컴포넌트로 묶고, 설정은 하나의 configuration object로 노출한다. 여러 signal interface는 하나의 hierarchical interface로 묶어 white-box probing 연결을 단순화한다. SVA는 interface 안에 두어 인스턴스화 시 자동 포함되도록 한다.
- **네임스페이스**: 패키지 scope의 모든 named 항목(class, constant, macro, type, enum literal 등)에 컴포넌트 고유 prefix를 붙인다.

확장 주제로는 다음이 다뤄진다. 형식 검증(formal)의 assume을 시뮬레이션 assertion으로 재사용하고, 전력 인지(power-aware) 시뮬레이션을 위해 드라이버·모니터·SVA에 전력 상태 표시자를 추가한다. RTL assertion과 AMS assertion은 성능 영향과 과신을 피하도록 선택적으로 켜고 끌 수 있어야 한다. CDC 어설션은 탑에서 재사용하되, bottom-up CDC waiver는 모드나 파생 제품에서 가정이 바뀔 수 있어 신중해야 한다. 추상화 수준이 다른 TLM 모델 재사용에는 프로토콜 계층과 물리 신호 계층의 분리가 필요하다. 커버리지 튜닝은 e의 AOP나 SystemVerilog의 factory 기반 클래스 치환으로 수행한다.

### 실험 결과 및 결론

본 문서는 정량적 실험이나 벤치마크 수치를 제시하지 않는다. 대신 여러 고객 프로젝트에서 관찰된 경험을 바탕으로 한 정성적 분석과 지침을 제공한다. 결론적으로 블록 공급자는 탑 레벨 통합자의 부담을 줄이는 방향으로 환경을 설계해야 하며, 가장 큰 실패 원인은 scoreboard의 active 연결, 불완전한 active/passive 설정, 흩어진 인터페이스 연결이라고 정리된다. 본문이 잘려 있어 커버리지 튜닝 이후의 세부 내용은 여기서 다루지 않았다.
