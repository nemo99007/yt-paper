# Finding a Needle in a Haystack: A Novel Log Analysis Method with Test Clustering in Distributed Systems

[:material-open-in-new: 원문 보기](https://dvcon-proceedings.org/wp-content/uploads/Finding-a-Needle-in-a-Haystack-A-Novel-Log-Analysis-Method-with-Test-Clustering-in-Distributed-System-1.pdf){ .md-button .md-button--primary target=_blank }

> 수십만 개 테스트의 시뮬레이션 로그에서 추출한 컴포넌트를 TF-IDF·PCA/SVD로 벡터화해 K-means로 군집화하고, 군집별 우선순위 알고리즘으로 테스트 순서를 재배열해 90% 에러 검출 시간을 약 80% 줄인(368.57h→73.08h, 산출값) 검증 자동화 방법이다.

## 핵심 인사이트

- 핵심 아이디어는 테스트 이름이 아니라 시뮬레이션 로그에서 추출한 컴포넌트(Task, Function, Sequence, UVM/사용자 정의 에러 등)를 feature로 쓰는 것이다. 논문은 이 방식이 테스트 이름 기반 군집보다 군집이 더 촘촘하게 나타난다고 주장한다(Figure 3 비교, 정량 지표는 제한적).
- 90% 에러 검출까지 걸린 시간 기준으로 Without-TCP(368.57h) 대비 Farthest-First(73.08h)가 가장 빨랐고, 이는 원 데이터로 약 80% 감소에 해당한다. 다만 단일 프로젝트 데이터, 단일 실행 결과 기반이라 일반화와 통계적 유의성은 검증되지 않았다.
- 가중치 클러스터링은 특정 critical 에러(레지스터 접근 등)를 19h 만에 찾았지만(단순 클러스터링 45h), 전체 90% 검출 시간은 최대 3일 지연되었다. 즉 '특정 에러의 조기 발견'과 '다양한 에러의 조기 발견' 사이의 trade-off를 설정 가능한 하이퍼파라미터로 다룬다.
- 예상과 달리 Error-Count/Runtime-wise 알고리즘이 최적이 아니었다. 저자들은 컴포넌트 버전이 바뀌면서 에러 수와 런타임이 달라졌기 때문으로 추정하며, 이력 기반 개선이 필요하다고 언급한다.
- 시스템 측면에서는 모델을 메모리에 상주시키는 in-memory 추론(응답 20~40초 → 평균 2초, 캐시 시 1초 미만)과 Spark/MongoDB 기반 분산 로그 처리, Airflow DAG로 로그 수집→군집화→재정렬을 사람 개입 없이 자동화한 구조가 핵심이다.

## 상세 요약

### 배경 및 문제 정의

디지털 설계의 복잡도가 증가하면서 검증 비용도 함께 늘고 있다. 본문은 설계 검증이 전체 공정의 약 70%를 차지한다고 인용하며(참고문헌 [1][2]), 검증 엔지니어가 여러 테스트에서 발생하는 공통 에러를 반복적으로 디버깅하는 작업과, 개발 후반에야 발견되는 치명적 에러 문제를 주요 과제로 제시한다. 기존에는 엔지니어의 설계 도메인 지식에 의존해 테스트 우선순위를 수동으로 정했는데, 이는 시간과 노력이 많이 든다.

따라서 본 논문의 목표는 (1) 시뮬레이션 로그 기반 군집화, (2) 군집 내 테스트 우선순위 결정, (3) 이를 운영할 수 있는 확장 가능한 ML 시스템 아키텍처를 제안하는 것이다. 목적은 "지정한 비율(예: 90%)의 에러를 가능한 한 빨리 검출"하는 것이다.

### 핵심 아키텍처 및 방법론

처리 흐름은 세 단계로 구성된다.

```mermaid
flowchart LR
    A[시뮬레이션 로그] --> B[컴포넌트 추출 및 중복 제거]
    B --> C[TF-IDF 벡터화]
    C --> D[PCA 또는 SVD 차원 축소]
    D --> E[가중 K-means 군집화]
    E --> F[군집별 TCP 알고리즘 선택]
    F --> G[우선순위 기반 회귀 실행]
```

**1. 데이터 전처리**: 중복 컴포넌트를 제거하고 토큰화한 뒤 TF-IDF로 벡터화한다. 차원은 PCA 또는 SVD로 줄이며, 본문 데이터에서 PCA는 차원을 92%, SVD는 85%로 줄였다고 보고한다. 원래 컴포넌트는 3,990개 feature였다.

**2. 군집화**: K-means를 사용하며, K는 Silhouette score와 Elbow method로 정한다(0~30 범위에서 Silhouette 최대값 선택, 30 이상은 Elbow 기준으로 의미 없다고 판단). 컴포넌트는 Non-error 타입(Task, Function, Sequence 등)과 Error 타입(툴 에러, 사용자 정의 에러)으로 나뉘며, 각각에 가중치 행렬 $W_c$, $W_e$를 곱한다. 하이퍼파라미터 $\alpha$(전체 컴포넌트 가중치), $\beta$(전체 에러 가중치), $w$(개별 항목 가중치)로 조절한다. 논문 본문에는 가중치 식이 그림 형태로만 들어가 있어 정확한 수식은 원문을 참조해야 한다.

**3. 테스트 우선순위(TCP)**: 다음 다섯 가지를 비교했다.
- Without-TCP: 기존 방식(군집화 없이 원래 순서대로 실행)
- Random: 군집에서 무작위 샘플링
- Farthest-First: 군집 중심에서 가장 먼 테스트부터 선택
- Closest-First: 군집 중심에서 가장 가까운 테스트부터 선택
- Error-Count/Runtime-wise: 에러 종류 수가 많고 런타임이 짧은 테스트를 우선

알고리즘은 각 군집에서 상위 테스트를 샘플링해 회귀를 돌리고, 모든 에러가 검출될 때까지 반복한다.

**시스템 아키텍처**: 
- 추론 측면: Nginx(로드밸런싱·캐싱), Gunicorn(WSGI), Django 웹 서버 구성을 사용하고, 모델은 thread-safe Singleton 패턴으로 한 번만 메모리에 로드한다. 논문은 이로써 모델 메모리 공간 복잡도를 O(N)에서 O(1)(N은 스레드 수)로 줄인다고 설명한다.
- 분산 처리: Spark와 MongoDB를 사용하고, 로그 처리가 독립적이라 병렬화에 유리하다고 본다.
- 자동화: 기존 검증 자동화 시스템[10]에 Airflow DAG로 데이터 수집, 전처리, 하이퍼파라미터 탐색, 모델 배포 파이프라인을 추가했다. 회귀가 끝나면 파이프라인이 자동으로 실행된다.

### 실험 결과 및 결론

평가 데이터는 한 검증 프로젝트의 수십만 개 테스트다. 평가 지표는 90% 에러를 검출하는 데 걸린 시간과 테스트 수다.

| TCP 알고리즘 | 90% 검출 시간 / 전체 실행 시간 | 90% 검출에 필요한 테스트 비율 |
|---|---|---|
| Without-TCP | 368.57h / 459.52h (80.2%) | 100% |
| Farthest-First | 73.08h / 315.37h (23.2%) | 76.1% |
| Closest-First | 166.89h / 288.22h (57.9%) | 97.7% |
| Random | 96.7h / 325.25h (29.7%) | 87.5% |
| Error-count/Runtime-wise | 106.79h / 386.02h (27.7%) | 90.6% |

- Farthest-First가 가장 빨랐다. 이는 Without-TCP 대비 약 80% 감소(산출값)이고, 테스트 수는 23.9% 감소했다고 본문에 기술되어 있다(표의 76.1%와 대응).
- 중심에서 먼 테스트가 더 다양한 에러를 찾았다는 해석을 제시했다.
- Error-Count/Runtime-wise는 기대와 달리 성능이 낮았으며, 컴포넌트 버전 간 차이 때문이라고 추정한다.
- 가중 군집화에서는 특정 critical 에러(레지스터 접근 관련)를 19시간에 찾아 단순 군집화(45시간)보다 빨랐지만, 90% 검출 시간은 최대 3일 늦어졌다.
- 시스템 추론 시간은 큐잉 환경에서 20~40초에서 평균 2초로 줄었고, 캐싱 사용 시 1초 미만이었다.

**결론 및 한계**: 본문은 군집 기반 TCP가 기존 순서보다 검증 시간을 크게 줄이며, 가중치와 알고리즘을 목적에 따라 선택할 수 있다고 결론짓는다. 한계로는 (1) 컴포넌트 이름이 바뀌어도 동작이 같을 수 있어 문맥을 고려해야 한다는 점, (2) K-means만 사용했다는 점, (3) 특정 프로젝트 버전에 기반하므로 이력을 반영하지 못한다는 점을 저자들이 직접 언급한다. 또한 단일 프로젝트 데이터, 반복 실험에 따른 분산 보고 없음, 가중치 수식의 구체적 값 미공개 등은 재현 시 확인이 필요하다. 본문이 일부 그림 중심이어서 수식과 실험 설정 세부 사항은 제한적으로만 확인할 수 있다.
