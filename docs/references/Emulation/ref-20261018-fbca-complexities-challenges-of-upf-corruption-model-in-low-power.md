## 핵심 인사이트

- 에뮬레이터는 실리콘 기반이라 본질적으로 2-state이므로, x 기반 corruption/initialization/propagation은 '0/1/random/inverted' 매핑으로 근사할 수밖에 없고, 이는 디버그 가시성만 흉내 내는 것이라는 점이 핵심 한계다.
- 시뮬레이터는 RTL을 이벤트 기반으로 평가하지만 에뮬레이터는 합성된 gate-netlist를 실행하므로, x-pessimism/optimism 차이로 인해 RTL 시뮬레이션과 에뮬레이션 결과가 x가 포함된 상황에서 일치하지 않을 수 있다.
- 전력 도메인이 꺼졌을 때 메모리/FIFO를 x로 만드는 것은 하드웨어 비용이 커서, 논문은 자동 생성되는 memory wrapper로 런타임 비용 없이 corruption을 구현하는 방식을 제안한다. 도식 결과에서 wrapper 적용 시 메모리 내용이 x로 올바르게 corrupt되는 것을 보였다.
- Table 3 비교에서 4-state 에뮬레이션은 시뮬레이션과 거의 동일한 결과를 보였고, 차이는 time 0에서 deposition 동작 정도에 그쳤다. 따라서 4-state 에뮬레이션은 시뮬레이션과 결과 비교가 가능하다는 장점이 있다.

## 상세 요약

### 배경 및 문제 정의

UPF(IEEE 1801)는 저전력 의도(intent)를 기술하는 언어일 뿐 아니라 검증·구현까지 포괄하는 명령 체계다. 저전력 설계 검증에서는 전력이 꺼진 도메인의 신호와 순차 소자를 x로 corruption하고, x가 ON 도메인으로 전파되는지, 전원 복구 후 레지스터가 x 상태로 초기화되는지를 확인해야 한다. 따라서 4-state(0, 1, x, z) 로직이 필수적이다.

시뮬레이터는 4-state를 지원하지만 용량과 이벤트 기반 실행 특성상 다중 전원 시퀀싱이 포함된 대규모 워크로드를 실행하기 어렵다. 반면 하드웨어 에뮬레이터는 cycle-based로 MHz 대 속도와 대규모 설계(약 10 BG) 수용이 가능하지만, 실리콘으로 구현되어 2-state(0/1)만 지원한다. 이 간극이 논문의 출발점이다.

문서는 corruption의 정의를 UPF LRM 기준으로 제시한다. 전원 공급이 줄거나 끊긴 로직이 corrupt 값을 가지는 것이며, 4-state에서는 x, 2-state에서는 0 또는 1로 표현된다.

### 핵심 아키텍처 및 방법론

논문은 다음 관점을 정리한다.

1. **x-pessimism / x-optimism 구분**: 시뮬레이터가 실제로 0/1인데 x를 내면 pessimism, 실제 x인데 0/1을 내면 optimism이다. RTL 시뮬레이션과 gate-level 합성 결과의 불일치(simulation-synthesis mismatch)의 근원이다.

2. **Corruption 모델**: 전원이 꺼진 인스턴스의 모든 순차 소자와 해당 인스턴스가 구동하는 신호는 corrupt되며, 전원 OFF 동안 프로세스는 비활성화된다. 전원 복구 시 continuous assignment는 다시 평가되고 순차 소자는 다음 클록에 재평가된다. 2-state 신호는 0으로, 4-state 신호는 x로 초기화된다.

3. **시뮬레이터 모드 vs. 에뮬레이터**: 시뮬레이터는 SV LRM(기본), CAT(Compute As Ternary, 하드웨어와 유사한 낙관적 전파), FOX(Forward Only X, 보수적 전파) 모드를 가진다. 논문은 에뮬레이터가 RTL을 gate-netlist로 합성하므로 CAT 모드와 유사한 방식만 채택한다고 주장한다.

4. **에뮬레이터 2-state 접근**: 2-state 에뮬레이션은 `create_power_domain`의 power_down_states/power_up_states 옵션으로 {high, low, random, inverted} 값을 지정한다. 디버거가 x로 태깅하는 것은 시각화용일 뿐 실제 x 전파는 불가능하다.

5. **4-state 에뮬레이션 구현**: 메모리/FIFO는 전원 OFF 시 x로 만들기 비싸다. 논문은 (a) 랜덤 값 로드(시간 소요), (b) 외부 로직으로 갱신(추가 자원과 디버그 필요)을 대안으로 들고, 자동 생성되는 **memory wrapper**를 제안한다. 이는 메모리 주소/제어 신호에 x가 있을 때 non-bit-blasted 메모리에서 x가 0으로 해석되는 문제도 해결한다.

### 실험 결과 및 결론

- **Table 2 (순차 소자 corruption)**: 시뮬레이터와 4-state 에뮬레이터는 latch, FF, 레지스터를 모두 x로 corrupt한다. 2-state 에뮬레이터는 0/1로 corrupt한다. 메모리는 시뮬레이터가 x로 corrupt하는 반면 에뮬레이터는 memory wrapper를 사용하므로 구현 방식이 다르다.

- **Table 3 (상태 전이별 비교)**: ON/OFF, OFF→ON, 리셋, ISO clamp, RET save/restore 등 상태 전이 시나리오에서 시뮬레이터와 4-state 에뮬레이터 결과가 거의 같다. 차이는 time 0 swap-in 시점의 x→0 deposition 하나뿐이며, 이는 에뮬레이션에서만 동작한다. 2-state 에뮬레이터는 default 0 또는 random을 보인다.

- **Figure 6/7 (메모리)**: wrapper 없이 전원 OFF 후 `out`은 x지만 메모리 덤프는 여전히 `00001111`로 corrupt되지 않는다. wrapper를 쓰면 덤프도 `xxxxxxxx`로 corrupt되어 시뮬레이션과 일치한다.

**결론**: 4-state 에뮬레이션은 UPF corruption을 시뮬레이션과 호환되는 방식으로 표현할 수 있으며, 메모리 wrapper가 핵심 구현 요소다. 단, 실제 RTL과 gate-netlist의 x 해석 차이는 완전히 제거되지 않는다. 저자들은 향후 4-state와 2-state corruption 모델이 emulation capacity(빌드 시 gate 크기)와 run-time clock 주파수에 미치는 영향을 연구할 계획이라고 밝혔다.

*참고: 본문의 정량 성능 수치(capacity/frequency 영향 등)는 제시되지 않았으며, 실험 결과는 표와 파형 정성 비교에 기반한다.*"
