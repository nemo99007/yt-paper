    Continuous Integration in SoC Design: Challenges and Solutions¶

    원문 보기

    GitLab CI, Jacamar CI 커맨드 어댑터, 기존 HPC 스케줄러(Slurm 등)를 결합해 추가 HPC 자원 없이 SoC 빌드·시뮬레이션 CI를 구축하고, 15개월 프로젝트에서 1,344건의 통합 실패를 조기 포착한 사례를 보고한 논문.

    항목 내용
    저자/출처 Liu Wei, Li Jianjun, Yang Liangfeng, Li Liang (SDTECH Information Technology, Beijing, China) — 학회명 명시 없음
    유형 PAPER
    카테고리 EDA
    ID ref-20261018-ee89

    핵심 인사이트¶

    • CI 도입의 핵심 난제는 자원 부족이 아니라 HPC 스케줄러와 CI 플랫폼의 비호환성이며, 이를 Jacamar CI 같은 커맨드 어댑터 계층으로 분리하면 CI 시스템 자체를 단순하게 유지할 수 있다.
    • CI 테스트 결과는 시뮬레이터 exit code(0=Pass, 非0=Fail)에만 의존하므로, 기존 regression 스크립트가 exit code를 정확히 반환하도록 만드는 것이 CI 연동의 최소 조건이다.
    • Git 저장소는 NFS 같은 네트워크 드라이브가 아닌 로컬 디스크에 두어야 명령 지연이 크게 줄고, 대규모 저장소는 scalar/sparse checkout(git 2.38+), 대용량 파일은 Git LFS(락 기능 포함)로 보완한다.
    • CI 작업을 트리거한 사용자의 신원으로 HPC 잡을 제출하면 실패 시 기존 빌드 산출물로 파형 덤프 재시뮬레이션이 가능하고, 팀별 HPC 자원 정책과 잡 수 제한도 자연스럽게 지킬 수 있다.
    • 보고된 효과(3,303 merge, 8,213 pipeline, 1,344 실패 조기 포착, 약 3,360시간 절감)는 저자 측 추정치로, 대조군 없이 과거 데이터에 기반한 값이므로 일반화에는 주의가 필요하다.

    상세 요약¶

    배경 및 문제 정의¶

    대규모 SoC 설계에서 CI를 도입하려면 다음과 같은 어려움이 있다고 저자들은 설명합니다.

    • HPC 인프라와의 비호환성: 빌드·시뮬레이션은 HPC 잡 스케줄러(Slurm, LSF, PBS 등)로 실행되는데, 일반 CI 도구는 이를 바로 지원하지 않습니다. 전용 컴퓨팅 자원을 추가하면 자원이 적을 때는 대규모 병렬 테스트가 어렵고, 많이 추가하면 비용이 커지는 딜레마가 있습니다. 정기 실행, 다중 merge 묶음 실행, 큐 방식 등 기존 시도들은 실시간성이 떨어지거나 시스템이 복잡해집니다.
    • Git 도입의 문제: 소프트웨어 도구를 최대한 활용하려면 Git을 써야 하지만, Git은 대형 저장소 성능 저하, 바이너리 merge 충돌, 대용량 파일 관리 문제가 있습니다. Perforce나 SVN은 이 부분에서 상대적으로 강점이 있으며 바이너리 파일 락을 지원합니다.

    본 논문은 이 두 문제를 HPC 자원의 시간적 보완성(개발 초기에는 HPC 여유, 후기에는 regression 증가)을 활용해 추가 자원 없이 해결하는 것을 목표로 합니다.

    핵심 아키텍처 및 방법론¶

    1. 구성 요소

    논문은 CI 흐름을 다음 컴포넌트로 나눕니다.

    컴포넌트 역할 본 논문의 선택
    Version Control System 코드·테스트·설정 저장, webhook, 브랜치 전략, 코드 리뷰 GitLab (Community)
    CI Platform 파이프라인 정의, 실행, 모니터링, 결과 보고 GitLab CI
    Command Adapter CI 명령을 스케줄러 명령으로 변환 (예: sim -b a_test → srun -n 1 sim -b a_test) Jacamar CI
    Job Scheduler 잡을 HPC 노드에 분배 Slurm 계열
    HPC 실제 빌드·시뮬레이션 수행 기존 서버 클러스터

    2. 실행 흐름

    flowchart LR
    A[개발자 push] --> B[Webhook: MR 트리거]
    B --> C[GitLab Runner: 브랜치 clone<br/>파이프라인 ID 디렉터리]
    C --> D[Jacamar CI: 명령 변환]
    D --> E[Slurm: 노드 할당]
    E --> F[HPC: build / sim 실행]
    F --> G[로그·결과를 GitLab 웹에 반환]

    3. 인프라 토폴로지

    • Git 서버, CI runner, 사용자 작업 서버는 각자 로컬 디스크에 Git 저장소를 둡니다.
    • Runner와 사용자 작업 서버의 로컬 스토리지는 NFS로 공유 파일 시스템에 노출되어 HPC가 코드를 읽을 수 있습니다.
    • Git clone/push는 Ethernet으로 로컬 저장소와 Git 서버 사이에서 직접 수행됩니다.

    4. 검증 워크플로우

    • 목표: main 브랜치는 항상 기본 오류가 없는 기준 상태를 유지합니다. main은 직접 push를 받지 않고 merge만 허용합니다.
    • RTL freeze 이전에는 main 하나만 장기 브랜치로 유지하고, 기능 추가·버그 수정마다 개인 브랜치를 만듭니다.
    • Merge request마다 IP·서브시스템·SoC 레벨의 CI 테스트(build + simulation)를 실행합니다. Build는 병렬로 수행되고, 각 build가 끝나면 그에 딸린 simulation이 병렬로 시작됩니다. 하나라도 실패하면 merge할 수 없습니다.
    • 개발자는 push 전에 git rebase main을 수행해 merge 후 실패 가능성을 줄입니다.
    • Merge 후 main에서도 CI를 다시 실행해 merge로 인한 이상과 문제를 유발한 merge를 식별합니다.
    • 자동 테스트는 속도를 위해 파형을 덤프하지 않습니다. 실패 시에는 트리거한 사용자의 권한으로 생성된 빌드 산출물을 재사용해 덤프 옵션으로 재시뮬레이션합니다.
    • 랜덤 변수로 인한 간헐적 결과 차이를 막기 위해 CI 테스트에는 고정 random seed를 지정합니다.
    • 설계 변경으로 검증 코드가 깨져 DE가 검증 코드를 수정할 의무가 없는 경우, DV가 DE의 remote 브랜치 커밋을 cherry-pick해 main에 반영하는 협업 방식을 제시합니다.

    5. 회귀 스크립트 확장

    • Python 기반 regression 도구를 사용하며, CI에서는 단일 테스트 단위로 호출합니다 (예: sim -t example_test_a). Exit code 0은 Pass, 非0은 Fail입니다.
    • build와 sim을 분리 실행할 수 있습니다 (sim -b example_build, sim -t example_test_a -so).
    • 빌드 옵션과 시뮬레이션 옵션은 YAML로 관리합니다. tag 키로 태그 기반 일괄 실행을 지원합니다.
    • 의존성을 가진 자식 파이프라인을 만들기 위해 sim -genci -tag ci 명령을 추가했습니다. 부모 파이프라인이 이 명령으로 build/sim job을 담은 자식 파이프라인 스크립트를 생성하면, build 성공 후에 해당 sim job이 제출됩니다.

    6. Runner 및 Jacamar CI 설정

    • GitLab Runner의 custom executor로 Jacamar CI를 지정합니다.
    • Jacamar 설정에서 custom_build_dir를 true로 두면 ${CI_PIPELINE_ID}별 디렉터리에 코드를 clone하고 시뮬레이션합니다.
    • group_permissions를 true로 두면 같은 Linux 그룹 사용자끼리 로그와 파형을 볼 수 있습니다.
    • 파이프라인이 끝나면 root 권한의 스크립트가 매일 정오에 24시간 이상 지난 디렉터리를 삭제합니다.

    7. Git 대용량 문제 해결 방법

    문제 본 논문의 해법
    저장소 파일 수 증가에 따른 명령 지연 저장소를 NFS에서 로컬 디스크로 이전, 필요하면 scalar로 최적화
    작은 작업에도 전체 checkout 필요 git 2.38+ scalar clone의 sparse checkout 사용
    대용량 파일 이력이 저장소를 키움 Git LFS 사용
    바이너리 merge 충돌, 락 부재 Git LFS의 lock/unlock 기능 사용
    서드파티 라이브러리 관리 저장소 밖(NFS 마운트)에 두고, 버전 경로를 담은 filelist를 저장소에서 관리

    실험 결과 및 결론¶

    실제 프로젝트 적용 결과 (논문 보고 수치)

    • 한 파이프라인은 19개 testbench build와 23개 simulation job으로 구성되며 1시간 이내에 완료됩니다. 저자들은 같은 종류의 프로젝트에서 수동 통합·테스트에 하루가 걸렸다고 비교합니다.
    • 개발 피크 시기에는 하루 최대 40개 파이프라인이 트리거되었고, 동시에 7~8개가 실행되었습니다.
    • 15개월 개발 기간 동안 41명의 개발자가 3,303회 merge를 수행했고, 8,213개 파이프라인이 실행되어 6,743건 성공, 1,344건 실패를 기록했습니다.
    • 개발자는 CI 실패 시 평균 5분 안에 원인을 찾았으며, 기존 흐름에서는 30분 이상, 일부는 24시간 이상 걸렸다고 보고합니다.
    • 과거 프로젝트에서 통합 이슈 1건당 평균 2.5시간이 소요되었다는 가정으로, 1,344건을 조기 포착해 약 3,360시간을 절감했다고 추정합니다.

    결론

    저자들은 GitLab CI, 맞춤형 regression 스크립트, 기존 HPC 인프라를 결합해 추가 하드웨어 투자 없이 가볍고 효율적인 CI를 구현했다고 결론짓습니다. 주요 장점은 빠른 오류 탐지, 버그 전파 감소, main 브랜치 무결성 유지, HPC 활용 최적화입니다.

    한계 및 주의점

    • 절감 시간(3,360시간)은 과거 데이터 기반의 추정치이며, 대조군 실험이나 통계적 검증은 제시되지 않습니다.
    • 본문에 CI 자체 성능 지표(잡 대기 시간, 스케줄러 큐 지연, 비용 비교 등)에 대한 정량 분석은 적습니다.
    • Figure 5~7의 상세 내용과 Figure 1~4의 세부 구성은 본문 텍스트로만 확인되어, 그림에서만 드러나는 정보는 반영하지 못했습니다.
    • 학회/저널명은 원문에 명시되어 있지 않습니다.
